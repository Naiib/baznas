# Divisi Penerimaan ZIS — Implementation Plan

> Dokumen ini untuk Antigravity/coding agent lokal. Jalankan task secara berurutan, satu commit kecil per task, dan jangan menghapus modul lama sebelum Task 15 selesai.

## Goal

Membangun ulang Divisi Penerimaan untuk seluruh penerimaan Zakat, Infak, dan Sedekah dari portal publik, transfer bank, QRIS, tunai, dan jemput zakat; dengan validasi Staff, approval Kepala Bagian untuk transaksi berisiko/nominal >= Rp10.000.000, rekonsiliasi, audit trail, dan export laporan PDF/Excel.

## Architecture

Gunakan namespace frontend `/penerimaan/*` dan endpoint backend `/api/penerimaan/*`. UI memakai pola workspace Penyaluran yang sudah stabil: dashboard berbasis periode, tabel desktop, card list mobile, detail drawer, sticky action, dan role-aware actions. Backend tetap menjadi sumber otorisasi; kontrol UI hanya menyembunyikan aksi yang pasti tidak diizinkan.

## Tech Stack

- Next.js 16 App Router, React 19, TypeScript 5.8 strict mode.
- Tailwind CSS v4, Manrope, lucide-react, Recharts.
- Express 5, PostgreSQL melalui repository yang sudah ada, ExcelJS, PDFKit.
- Vitest + Testing Library untuk frontend; Node test runner untuk backend.

## Global Constraints

- Scope awal hanya Zakat, Infak, dan Sedekah.
- Kanal awal: Portal publik, Transfer bank, QRIS, Tunai/Jemput Zakat.
- Master kanal dapat ditambah, dinonaktifkan, dan diubah Admin.
- Role: Staff Penerimaan, Kepala Bagian Penerimaan, Admin.
- Default approval threshold: Rp10.000.000 per transaksi; dapat diubah Admin dari Pengaturan.
- Semua transaksi digital tetap masuk antrean validasi Staff.
- Transaksi manual, nominal >= threshold, duplikat, data tidak lengkap, dan transaksi berisiko memerlukan approval Kepala Bagian.
- Kepala Bagian tidak boleh menyetujui transaksi yang dibuat sendiri.
- Transaksi posted tidak boleh dihapus; koreksi dilakukan dengan reversal yang tercatat.
- Production fail-closed ketika PostgreSQL tidak sehat; tidak boleh fallback ke SQLite/demo.
- Semua perubahan penting memiliki audit trail immutable.
- Tidak ada asset bitmap wajib; UI harus dapat dibangun dengan komponen HTML/CSS/SVG.
- Setiap task berakhir dengan test yang relevan dan satu commit.

## Core Workflow

### Digital transaction

```text
Provider/portal → webhook signature + idempotency → normalisasi
→ cari/buat Muzakki → duplicate/risk check → Menunggu Validasi
→ validasi Staff → approval Kepala jika flag/nominal besar
→ rekonsiliasi → Posted → kuitansi + agregasi Penyaluran
```

### Manual transaction

```text
Staff membuat draft → upload bukti → validasi kelengkapan
→ validasi Staff → approval Kepala → rekonsiliasi → Posted
```

### Cash/pick-up batch

```text
Staff mencatat penerimaan → batch setoran → bukti serah-terima
→ setoran kas/rekening → rekonsiliasi nominal → Kepala menutup batch → Posted
```

Status canonical:

`Masuk`, `Menunggu Validasi`, `Terverifikasi`, `Menunggu Approval`, `Menunggu Rekonsiliasi`, `Terekonsiliasi`, `Posted`, `Ditolak`, `Duplikat`, `Data Tidak Lengkap`, `Perlu Klarifikasi`, `Dispute`, `Dibatalkan`.

## Acceptance Criteria

- Staff can receive, validate, reconcile, and submit transactions without seeing forbidden approval actions.
- Kepala Bagian can approve only eligible transactions and cannot approve their own submissions.
- Admin can manage channels, accounts, threshold, roles, and recovery actions.
- Digital, manual, cash, and pick-up flows have visible statuses and audit history.
- Posted totals reconcile with source data and are available to Penyaluran only after posting.
- PDF, Excel, and CSV exports match active filters and permissions.
- No old penerimaan route remains active after cutover.
- Desktop, tablet, and mobile layouts remain usable without forced horizontal text wrapping.
- PostgreSQL failure causes an unhealthy service, never demo/SQLite fallback.

## Execution Rule for Antigravity

Implement one task at a time. For every task: write failing tests first, run the focused test to observe failure, implement the smallest change, run focused plus relevant regression tests, inspect the diff, then commit. Stop and report if a task changes the domain contract or requires a new product decision; do not silently expand scope.
